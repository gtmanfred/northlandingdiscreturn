# Disc ID Column — Stable Spreadsheet Identity

Date: 2026-08-05
Status: Approved

## Problem

The spreadsheet has no stable key for a disc. `disc_import.py` identifies an existing
disc with a fuzzy composite key — `input_date + manufacturer + model + colors + phone`
(`DiscRepository.find_by_import_key`). Any edit to those fields makes the row look new,
so the import creates a duplicate instead of updating. Correcting a typo in a color or
attaching a phone number can silently fork a disc into two records.

## Goal

Add a `ID` column to the `Current` sheet holding a stable uuid per disc. The import uses
it as the primary identity: an ID that exists in the DB updates that disc, an ID that does
not exist creates a disc with that exact id. Rows with no ID keep today's fuzzy behavior.

## Scope

In scope:

* `Current` sheet only — the sole sheet the in-app import reads.
* In-app import pipeline (`app/services/disc_import.py`, preview/approve endpoints).
* Export (`app/services/disc_export.py`) so ids round-trip.
* A one-off backfill script reconciling existing DB discs with the sheet.

Out of scope:

* `scripts/import_discs.py` (standalone POST-per-row script) — unchanged.
* `No Number`, `Returned`, `Hopefuls` sheets — no ID column.
* Any change to `discs.id` values already in the DB. No primary keys are rewritten.

## Decisions and Trade-offs

**ID generated by spreadsheet formula, frozen to a literal via Paste Special > Values.**

The sheet is maintained across a mix of desktop Excel, Excel web, and Google Sheets, so
VBA was rejected — it does not run on web or in Sheets, and a row edited there would
silently get no ID. A formula built from `RANDBETWEEN`/`DEC2HEX` is native to every modern
Excel and to Sheets, and needs nothing installed.

No spreadsheet function provides non-volatile randomness: a live formula recalculates and
its uuid mutates, which would create duplicates on the next import. So the formula lives in
a helper column `L` and its output is frozen into `K` as literal text. The cost is a manual
step; section "Guardrails" is how that cost is made survivable.

Rejected alternative — server stamps the id and export writes it back to `K`. Cannot drift
and needs nothing in the sheet, but the id only materializes after an import plus a
re-download, so a freshly typed row has no identity in the file the admin is looking at.

## Spreadsheet Layout (`Current`)

File stays `.xlsx`. Rows 1–3 are title / subtitle / header; data starts at row 4.

| Col | Contents |
|-----|----------|
| A–J | Name, Phone, Mfr, Model, Color, Other, Code, Date found, Date returned, Date contacted (unchanged) |
| K   | `ID` — frozen literal uuid string |
| L   | `ID gen` — generator formula, ignored by the parser and by export |

`L4`, filled down past the last data row:

```
=IF($K4<>"",$K4,LOWER(DEC2HEX(RANDBETWEEN(0,4294967295),8)&"-"&DEC2HEX(RANDBETWEEN(0,65535),4)&"-4"&DEC2HEX(RANDBETWEEN(0,4095),3)&"-"&DEC2HEX(RANDBETWEEN(8,11),1)&DEC2HEX(RANDBETWEEN(0,4095),3)&"-"&DEC2HEX(RANDBETWEEN(0,65535),4)&DEC2HEX(RANDBETWEEN(0,4294967295),8)))
```

The `IF($K4<>"",$K4,...)` guard makes the freeze idempotent: where `K` already holds an id,
`L` echoes it back, so pasting the entire `L` range over `K` never clobbers an existing id.
Only blank `K` cells receive a newly generated uuid.

### Freeze procedure

Excel (Mac or Windows):

1. Select `L4` through the last data row.
2. Copy (`Cmd+C` / `Ctrl+C`).
3. Click `K4`.
4. Paste values only — Mac: `Cmd+Ctrl+V`, choose **Values**, OK. Windows: `Ctrl+Alt+V`,
   press `V`, `Enter`.
5. Verify: a `K` cell's formula bar shows raw text, not a leading `=`.
6. Save.

Google Sheets: copy the same `L` range, click `K4`, `Cmd/Ctrl+Shift+V` (Paste values only).

Rules: paste `L` → `K` only, never `K` → `K` or `K` → `L`; start at row 4, never include
rows 1–3; repeat after adding rows (a re-run over frozen rows is a no-op).

## Guardrails

A missed freeze is the failure mode this design has to absorb. Three checks:

1. **Live formula in `K`** — the row errors out and nothing is written. Message:
   `ID is a live formula — freeze with Paste Special > Values`.
2. **Duplicate ID within the sheet** — every row sharing that id errors out.
3. **Drift warning** — a row whose ID is unknown to the DB but whose fuzzy import key
   matches an existing disc is flagged in the preview as
   `possible duplicate — new ID but matches existing disc <id>`. It is still creatable; the
   admin decides. This is the net that catches a recalculated id.

Checks 1 and 2 are parse-time (row `error`, so the row lands in `plan.errors` and
`apply_import` skips it). Check 3 is plan-time and advisory.

## Components

### Parser — `app/services/disc_import.py`

`parse_current_sheet` currently loads with `data_only=True` and pads each row to 10 cells.
Changes:

* Pad to 11 cells; `cells[10]` is the raw ID.
* Load the workbook a second time with `data_only=False` to inspect `K` for a leading `=`.
  Formula detection cannot use the `data_only=True` pass, which yields the cached value.
* `ParsedDiscRow` gains `disc_id: uuid.UUID | None`.
* Empty `K` → `disc_id = None`. Non-empty and unparseable as a uuid → `error = "invalid ID"`.
  Formula in `K` → `error = "ID is a live formula — freeze with Paste Special > Values"`.
* After the row loop, detect repeated `disc_id` values and set the duplicate error on each
  participating row.
* `row_to_dict` / `row_from_dict` carry `disc_id` as a string (or `None`) so the staging
  JSON blob round-trips through `import_staging.rows`.

### Identity resolver — `app/services/disc_import.py`

One shared helper used by both `plan_import` and `apply_import`, so the preview cannot
disagree with what apply does:

```
resolve(row) ->
  row.disc_id is not None:
      disc_repo.get_by_id(row.disc_id)
        found     -> ("update", disc)
        not found -> ("create_with_id", None)   # + drift check against find_by_import_key
  row.disc_id is None:
      find_by_import_key(...)
        found     -> ("update", disc)
        not found -> ("create", None)
```

An ID match wins over a fuzzy match: if `K` names disc A while the fuzzy key would have hit
disc B, disc A is updated. `_compute_updates` and `_plan_diffs` are unchanged — they already
take `(existing, row, owner_id)` and are agnostic to how `existing` was found.

`create_with_id` passes the sheet's uuid through to the new disc. Welcome / heads-up SMS
enqueueing is unchanged: it fires on create, not on update, so re-importing a row with a
known ID sends nothing.

### Repository — `app/repositories/disc.py`

`DiscRepository.create` gains an optional `id: uuid.UUID | None = None`. When `None`, the
model default (`uuid.uuid4`) applies, so every existing caller is unaffected.

### Plan output — `app/services/disc_import.py`

Entries in `ImportPlan.created` gain `duplicate_warning: str | None`. `plan.to_dict()`
counts add `"possible_duplicates"`. Existing keys (`will_notify`, `skip_reason`, the
will-text / no-text split) are untouched.

### Export — `app/services/disc_export.py` and `app/routers/discs.py`

`"ID"` appended to `DISC_EXPORT_COLUMNS`, landing in column `K` and matching the sheet.
The export row builder in `export_discs` supplies `"ID": str(d.id)`. Exported ids are
already literal text, so a re-downloaded sheet needs no freeze for its existing rows. The
export does not emit the `L` helper column; a maintainer re-adds it if they intend to keep
editing that download.

### Backfill — `scripts/backfill_disc_ids.py`

One-off, run once before the first ID-aware import. Reads the DB (read-only), writes only
the spreadsheet.

* Args: `xlsx_path`, `--dry-run`, `--sheet` (default `Current`).
* For each data row with a blank `K`: resolve via `find_by_import_key` using the same
  parsing as the import. Match → write that disc's real uuid. No match → write a fresh
  `uuid4` (the next import then creates the disc with that id).
* Never overwrites a populated `K`.
* `--dry-run` prints matched / unmatched / already-populated counts and writes nothing.
* Ambiguity: `find_by_import_key` returns the first match, so two identical sheet rows both
  resolve to the same disc. The script reports rows whose resolved id was already claimed by
  an earlier row and leaves the later one blank rather than assigning a colliding id.
* DB access reuses the backend's async session and settings; no new dependency.

## Data Flow

```
Admin edits Current sheet, freezes L -> K
        |
        v
POST /discs/import/preview  (xlsx upload)
        |
   parse_current_sheet  -- reads K, flags formulas / dup ids / bad uuids
        |
   plan_import  -- resolve() per row -> created / created_with_id(+warning) / updated / unchanged / errors
        |
   import_staging row (rows JSON carries disc_id)
        |
        v
POST /discs/import/{id}/apply
        |
   apply_import  -- same resolve(); creates carry the sheet uuid; SMS only on create
        |
        v
GET /discs/export  -- writes real ids back into column K
```

## Error Handling

* Malformed uuid, live formula, duplicate sheet id, missing `Date found` → row error, row
  appears in `plan.errors`, skipped by apply. Existing behavior for `missing or invalid
  Date found` is unchanged.
* `Current` sheet or header row absent → `ValueError` → HTTP 422, as today.
* No new failure mode from an unknown ID: creating with a caller-supplied uuid cannot
  collide, because a colliding uuid would have been found by `get_by_id` and routed to
  update.

## Testing

Red first, one behavior per test.

`tests/test_disc_import.py`
* ID matching an existing disc updates it and does not create.
* Unknown ID creates a disc whose `id` equals the sheet value exactly.
* Blank ID falls through to the fuzzy path — existing tests must stay green.
* Malformed ID → error row, nothing written.
* Live formula in `K` → error row with the freeze message.
* Duplicate ID within the sheet → both rows error.
* ID match beats a conflicting fuzzy match.
* Re-import of a known ID sends no welcome / heads-up SMS.

`tests/test_disc_plan.py`
* Unknown ID whose fuzzy key hits an existing disc → `duplicate_warning` set, counted in
  `possible_duplicates`.
* Preview classification equals apply's outcome for each of the resolver's four branches.

`tests/test_disc_export.py`
* `ID` column present in `K` and equal to the disc's id.

`tests/test_backfill_disc_ids.py`
* Row matching a DB disc receives that disc's id.
* Unmatched row receives a syntactically valid uuid.
* Populated `K` is never modified.
* `--dry-run` leaves the file byte-identical.
* Second sheet row resolving to an already-claimed disc is left blank and reported.

## Rollout

1. Land parser, resolver, repository, plan, export changes with tests.
2. Add `K` / `L` to `discs.xlsx`, freeze once.
3. Run `backfill_disc_ids.py --dry-run`, review counts, then run it for real.
4. Freeze again (the script writes literals, so this is a no-op check).
5. Import preview against the backfilled sheet — expect near-zero creates. A large create
   count means the backfill mismatched and should be investigated before applying.
